## Appendix A: Changelog

> Dates are approximate to the work session; `git log` has the exact commits. The living status
> of what is built and what remains is `reference/ROADMAP.md`.

### Foundation
Migration off the legacy **Google AppSheet** application: the request form, the sequential
approver chain, status tracking, and the notification set rebuilt as a custom Apps Script SPA.
Design decisions versus AppSheet are recorded in `reference/ARCHITECTURE.md` §2 and §8.

### Attachments and certificates
Upload-before-submit (files land in Drive before any sheet row is written, so a failed upload
leaves no half-request), identity-gated serving, attachment grouping by resubmission cycle, and
automatic certificate generation on full approval with a row per PDF in `COC_PDFs`.

### Database normalization
A 35-column monolith split into purpose-built sheets behind the `Accessors.js` seam. Because the
seam reconstructs the previous data shapes from the timeline, the frontend contract stayed frozen
and the UI was barely touched.

### The certificate engine, rebuilt in code
Certificates had been generated by filling a Google Docs template. That template was an external
dependency with no version history and no review process, where one careless edit would silently
alter every certificate issued afterwards. Rendering in code put the certificate's design under
the same version control as the rest of the system, and allowed dropping the `documents` OAuth
scope.

### Security hardening
- **Callable surface: 118 → 27.** Roughly 90 internal helpers renamed to the private form, each
  remaining endpoint resolving identity server-side and authorizing before its first write, and a
  committed checker so the property is enforced by tooling rather than reviewer memory.
- **Formula injection closed** at every free-text write path.
- **Concurrent-write data loss closed**: two simultaneous submits could each compute the same
  next row and overwrite one another's attachment records.
- **A dormant duplicate email path deleted.** The `onSheetChange` trigger family held a complete
  second implementation of the notification system and was one trigger registration away from
  double-sending every workflow email with wrong-identity receipts.
- **Domain allowlist** enforced server-side, independent of the deployment setting.

### Cross-cycle approval history
The system had always recorded every action and never deleted any of it, but almost none was
visible: a requestor saw only returns, an approver saw only the current round, emails showed only
the latest. One chronological history is now rendered identically for requestors, approvers and
notification emails.

### Return flags and editable resubmit
Approvers may flag individual fields and documents with per-item comments. Resubmission became a
full prefilled editable form. Before this, **a requestor could not edit any field on resubmit**;
a wrong contract date was uncorrectable through the portal.

### Admin console
All-requests oversight plus group and approver-chain management, with an in-flight shrink guard,
chain-change notification to whoever newly holds a request, and an append-only `Admins_Log`.

### Scheduled jobs
Contract-expiry reminders in three stages, and approver nudges. The nudge cadence was later
changed from daily to **7 days, then every 3**.

### Supervisor feedback pass (14 August 2026)
Configurable `Locations` sheet replacing hardcoded options; per-field help tooltips; consolidated
resubmit page (the edit form *is* the page, with prior documents shown inline and flagged ones
highlighted); flag attribution by approver number; optional approve comments; compacted
single-entry history across all three renderers; standardized back-navigation; resolved-flag
history moved into the request timeline behind a dialog.

## Appendix B: Testing & QA

The full manual test pass is **`reference/TEST_SCRIPT.md`**, ordered for execution in one sitting
rather than grouped by feature, so a skipped step is visible.

Run it after every deploy, with these caveats:

- **Republish before testing.** A `clasp push` updates `/dev` only; email deep-links point at the
  last published `/exec`. Testing before republishing means chasing ghosts.
- **Test with a fresh request.** Emails freeze their links at send time.
- **Prefer a copy of the production spreadsheet** over live data.

**Quick smoke test:**
1. Sign in → a dashboard renders *(proves all 15 HTML includes resolved and the database is
   reachable)*
2. File a request with a real PDF → it appears in My Requests, a row lands in `Requests`, the
   file is in Drive, and Approver 1 is emailed
3. Return it with a flag → the requestor sees the flag highlighted and itemized in their email
4. Resubmit and approve → status reaches Fully Approved and the certificate PDF is attached to
   the requestor's email

> ⚠️ **The single most valuable assertion in the pass:** after running the expiry sweep, confirm
> **no `expiry_warning` entry and no `system` actor appears anywhere in a request's history.**
> Those system actions share the activity table with real approvals and are excluded only by an
> explicit allowlist (Part 0 §0.3).

## Appendix C: Security findings

The audit is documented in **`reference/FINAL_AUDIT_REPORT.md`**: what was found, what was fixed,
what was deliberately deferred, and why. `reference/COC_SYSTEM_PROFILE.md` §12 is the as-built
account of weaknesses, written for an external reviewer and deliberately including things that
are wrong with the system.

Applied hardening is summarized in Appendix A; the model itself is Part 0 §0.6.

**Deliberately open, recorded so it is not rediscovered as a defect:** approver emails are
configured by admins in `Group_Approvers` rather than validated against an employee directory,
because no such directory is available to this project. The mitigation is after-the-fact: the
approval history records every approver's identity, so an irregular approval is visible on the
record.

## Appendix D: Certificate rendering

The certificate is built as HTML by `buildCertificateHtml_()` in `backend/Certificate.js` and
converted to PDF in-process. There is no template file to edit; layout changes are code changes,
reviewed and version-controlled like any other.

Layout, fonts and the signatory block are specified in **`reference/COC_TEMPLATE_SPEC.md`**.

The signatory block renders **only the approvers who actually approved**, so a one-approver chain
produces one signature block rather than three, two of them empty. Approval dates and names come
from the timeline, not from the request row.
